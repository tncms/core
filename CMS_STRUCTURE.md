# TheNguyen CMS Architecture

> Permanent architecture reference for **TheNguyen CMS** (working name
> `laravel-cms`). This document describes how the codebase is organised
> today, the conventions every contributor (human or AI) must follow, and
> the roadmap that future modules, themes, and plugins will plug into.

Current version: **1.0.0-beta.7.1.5** (CategoriesWidget Strict Per-Locale Display).

> 📐 **Single source of truth:** [`CMS_ARCHITECTURE.md`](CMS_ARCHITECTURE.md)
> is the authoritative, code-verified architecture reference (schema,
> services, facades, helpers, routes, theme/menu/media systems, frontend
> rendering, extension points, and the rules for AI assistants). It
> explicitly separates **IMPLEMENTED** from **PLANNED**. This document
> (`CMS_STRUCTURE.md`) provides deeper design notes and the phased roadmap;
> when the two disagree, `CMS_ARCHITECTURE.md` (and the code) wins.

### Goals

- A **single, opinionated** Laravel + Filament foundation that can grow
  into a full CMS without rewriting plumbing.
- **First-class shared-hosting support.** The CMS must run on cPanel-style
  hosts where the document root is forced to `public_html`, and on hosts
  where the document root can be pointed at `/public`.
- **First-class VPS support** for Nginx / Apache / OpenLiteSpeed.
- A **plugin/theme architecture** (planned) where the core never needs to
  be edited to add features.
- **No vendor patches.** Everything we own lives under `app/`,
  `packages/thenguyen/`, `modules/`, and `themes/`.

### Compatibility targets

- **Shared hosting** with Apache + `mod_rewrite` (cPanel, DirectAdmin,
  Plesk).
- **VPS** with Nginx + PHP-FPM, Apache + PHP-FPM, or OpenLiteSpeed.
- **Local dev** on Laragon (Windows), Valet (macOS), or any Docker
  environment that exposes Laravel via `/public`.

## Core Philosophy

These rules are non-negotiable and apply to every future contribution.

1. **Never modify `vendor/`.** It is regenerated by Composer and any patch
   will silently disappear on the next `composer install`. If a vendor
   package needs changing, fork it or wrap it.
2. **CMS core lives in `packages/thenguyen/cms-core/`.** Anything that is
   "the CMS itself" (service providers, support classes, contracts,
   services, core models, base abstractions) belongs in this package.
   Application-specific glue lives in `app/`.
3. **Modules / plugins live in `modules/`.** Each module is a self-
   contained feature (e.g. `Blog`, `Page`, `Menu`). The CMS core
   discovers, loads, enables, and disables them. Modules must never edit
   the core to function.
4. **Themes live in `themes/`.** Each theme is a self-contained frontend
   presentation layer with its own layouts, partials, and source assets.
   Compiled / public assets are published into `public/themes/{slug}/`.
5. **Public assets only inside `public/`.** Anything browser-reachable
   (JS, CSS, fonts, uploads, theme builds, CMS-shipped vendor assets)
   must live under `public/`. Nothing under `app/`, `packages/`,
   `modules/`, `themes/`, `vendor/`, `storage/` is meant to be served
   directly.
6. **All requests go through `public/index.php`.** The deployment
   templates in `deployment/` exist to guarantee this even when the
   document root is forced to the project root.

### Current classes

**`TheNguyen\CMS\Providers\CmsServiceProvider`** — service provider
registered in `bootstrap/providers.php`. Today it:

- Merges `packages/thenguyen/cms-core/config/cms.php` into the `cms.*`
  config namespace.
- Registers the nine core service singletons in `register()`:
  `cms.settings`, `cms.slug`, `cms.html`, `cms.content`, `cms.taxonomy`,
  `cms.media`, `cms.menu`, `cms.theme`, and `cms.seo` — each also
  aliased to its manager class (`SettingsManager`, `SlugManager`,
  `HtmlSanitizer`, `ContentManager`, `TaxonomyManager`, `MediaManager`,
  `MenuManager`, `ThemeManager`, `SeoManager`). `ContentManager` receives
  both `cms.slug` and `cms.html`.
- Publishes the same file to `config/cms.php` under the tag
  `cms-config`.
- Registers the `theme::` view namespace (`ThemeManager::registerViews()`).
- Ensures `modules/`, `themes/`, `public/uploads/`, `public/themes/`,
  and `public/vendor/cms/` exist at boot.
- Loads the core routes (`routes/web.php` → `/cms-health`, then
  `routes/frontend.php` → public site routes, in that order).
- Registers Artisan commands when running in console
  (`cms:settings:clear-cache`).

> The authoritative binding/facade table is in
> [`CMS_ARCHITECTURE.md`](CMS_ARCHITECTURE.md) §3.

```php
<?php

namespace TheNguyen\CMS\Providers;

use Illuminate\Support\ServiceProvider;

class CmsServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->mergeConfigFrom(__DIR__.'/../../config/cms.php', 'cms');
    }

    public function boot(): void
    {
        $this->publishes([
            __DIR__.'/../../config/cms.php' => config_path('cms.php'),
        ], 'cms-config');

        // ensure runtime dirs + load routes
    }
}
```

### Settings Manager (Phase 2 — current)

The Settings Manager is the first stateful CMS subsystem. It owns the
`cms_settings` table, an Eloquent model, a service class, a facade, a
global helper, a Filament admin page, an Artisan command, and a seeder.

**Table — `cms_settings`**

| Column        | Type      | Notes                                          |
| ------------- | --------- | ---------------------------------------------- |
| `id`          | big int   | Primary key                                    |
| `group`       | string    | Nullable, indexed                              |
| `key`         | string    | Indexed                                        |
| `value`       | longText  | Nullable, JSON-compatible string               |
| `type`        | string    | `string`, `text`, `boolean`, `integer`, `float`, `array`, `json` |
| `is_public`   | boolean   | Whether the setting can be exposed publicly    |
| `autoload`    | boolean   | Whether the setting is preloaded into cache    |
| `description` | text      | Nullable human description                     |
| `timestamps`  | datetime  | `created_at`, `updated_at`                     |

Unique compound index: `(group, key)`.

The migration ships **inside the core package** at
`packages/thenguyen/cms-core/database/migrations/` and is loaded
automatically by `CmsServiceProvider::loadMigrationsFrom()`.

**Localized settings — `cms_settings_translate` (1.0.0-beta.6.2)**

Translatable settings store one value per language in a companion table;
`cms_settings` is unchanged and remains the permanent global fallback.

| Column      | Type     | Notes                                |
| ----------- | -------- | ------------------------------------ |
| `id`        | big int  | Primary key                          |
| `key`       | string   | Indexed; matches a `cms_settings` key |
| `locale`    | string   | Indexed                              |
| `value`     | longText | Nullable                             |
| `type`      | string   | Same type vocabulary as `cms_settings` |
| `timestamps`| datetime | `created_at`, `updated_at`           |

Unique compound index: `(key, locale)`.

Localized keys: `general.site_name`, `general.site_tagline`,
`general.site_description`, `seo.default_meta_title`,
`seo.default_meta_description`, `maintenance.title`, `maintenance.message`.
Permalink bases are **not** localized (they affect routing/sitemap/hreflang).

API on `SettingsManager`: `getLocalized()` / `localized()` (lookup order:
requested locale → CMS default locale → global `cms_settings` → default),
`setLocalized()`, `forgetLocalized()`, `isLocalized()`, `rawLocalizedValue()`,
`backfillLocalizedDefaults()`, `localizedHealth()`. Helpers:
`setting_localized($key, $locale = null, $default = null)` and
`cms_setting_localized()`. All lookups never throw.

**Setting key naming convention**

All setting keys use dot notation: `group.key`. Examples:

- `general.site_name`
- `general.site_description`
- `general.admin_email`
- `seo.default_title`
- `seo.default_description`
- `admin.brand_name`
- `system.deployment_mode`
- `theme.active`

Keys without a dot are stored with `group = null` and addressed by their
bare key. New groups (`module.*`, `plugin.*`, `theme.*`) are reserved for
future phases.

**`TheNguyen\CMS\Models\Setting`** — Eloquent model.

- Table: `cms_settings`
- Fillable: `group`, `key`, `value`, `type`, `is_public`, `autoload`, `description`
- Casts: `is_public => boolean`, `autoload => boolean`
- `fullKey(): string` returns `"{group}.{key}"` (or just `key` if no group).

**`TheNguyen\CMS\Services\SettingsManager`** — main service.

Resolved from the container under `cms.settings` (also bound by class
name). It is registered as a singleton in `CmsServiceProvider::register()`.

Public API:

```php
$settings->get(string $key, mixed $default = null): mixed;
$settings->set(string $key, mixed $value, ?string $type = null, array $options = []): void;
$settings->has(string $key): bool;
$settings->forget(string $key): void;
$settings->all(): array;
$settings->group(string $group): array;
$settings->clearCache(): void;
$settings->refresh(): array;
$settings->isCached(): bool;
```

Behavior:

- Dot notation: keys are parsed into `(group, key)` via `parseKey()`.
- Autoload cache: all rows with `autoload = true` are cached together
  under the cache key `cms.settings.autoload`. The cache is forever
  until invalidated. `set()` and `forget()` invalidate automatically.
- Type detection: when `$type` is `null`, `detectType()` infers it from
  the PHP value.
- Serialization (`serializeValue`):
  - `boolean` → `"1"` / `"0"`
  - `integer` / `float` → string cast
  - `array` / `json` → `json_encode(...)`
  - `string` / `text` → plain string
- Reading (`castValue`) reverses the same mapping.
- Graceful degradation: every public method checks
  `Schema::hasTable('cms_settings')`. If the table does not exist (e.g.
  before the first migration), reads return the default and writes are
  silently no-ops. This is what keeps `/cms-health` and the dashboard
  widget from 500-ing on a fresh checkout.

**`TheNguyen\CMS\Facades\Settings`** — accessor facade.

- Extends `Illuminate\Support\Facades\Facade`.
- `getFacadeAccessor()` returns `'cms.settings'`.
- Example:

  ```php
  use TheNguyen\CMS\Facades\Settings;

  Settings::get('general.site_name', 'TheNguyen CMS');
  Settings::set('admin.brand_name', 'Acme Co');
  ```

**`settings()` helper** — defined in
`packages/thenguyen/cms-core/src/helpers.php` and autoloaded via the
root `composer.json` `autoload.files` entry.

```php
settings();                                      // SettingsManager
settings('general.site_name');                   // mixed
settings('general.site_name', 'TheNguyen CMS');  // mixed
```

**`App\Filament\Admin\Pages\SettingsPage`** — Filament v5 page.

- Slug: `settings` → URL `/admin/settings`.
- Navigation: group `CMS`, icon `heroicon-o-cog-6-tooth`.
- View: `resources/views/filament/admin/pages/settings-page.blade.php`.
- Sections: General, SEO, Admin, System (read-only).

- `save()` persists only the editable fields and clears the cache.
- The page does **not** introduce a new Filament panel — it is

**`cms:settings-clear` Artisan command** — clears the autoload cache

### Content Core (Phase 3 — current)

The Content Core is the second stateful CMS subsystem. It owns the
unified content engine that backs **Pages** and **Posts**, the
**Taxonomy / Term** system, **translations**, **slugs**, and the WP-like
Filament admin surface.

#### Why Pages and Posts share `cms_contents`

WordPress treats pages and posts as the same underlying record type
discriminated by a `post_type` column. We follow that design because:

- It collapses two near-identical tables into one and lets us add new
  content types (`event`, `landing`, `product`) without schema changes.
- Cross-type features (revisions, comments, custom fields, media,
  permissions) only need to be implemented once.
- The Filament admin can still present them as two different
  navigation entries — `PageResource` and `PostResource` both target
  `Content`, but each scopes its query and form to its `type`.

The discriminator column is `cms_contents.type`. Today it accepts
`page` and `post`. Future types can be introduced without a migration.

#### Tables

| Table | Purpose |
| ----- | ------- |
| `cms_contents` | One row per content record (page or post). Holds type, status, author, parent, template, comment status, sort order, published_at, soft deletes. |
| `cms_content_translations` | Per-locale title, slug, excerpt, content, SEO fields. Unique on `(locale, slug)` and `(content_id, locale)`. |
| `cms_taxonomies` | One row per taxonomy (category, tag, custom). Discriminated by `content_type` so the same `slug` can be reused across content types. |
| `cms_terms` | One row per term (category/tag value). Hierarchical via `parent_id`. Soft deletes. |
| `cms_term_translations` | Per-locale name, slug, description, SEO fields. Unique on `(locale, slug)` and `(term_id, locale)`. |
| `cms_content_terms` | Many-to-many between contents and terms. |
| `cms_slugs` | Route lookup table. Stores `(reference_type, reference_id, locale, slug, prefix, full_path, is_primary)`. Future-ready for the frontend router. |

All seven tables ship inside the package's `database/migrations` and
load automatically via `CmsServiceProvider::loadMigrationsFrom()`.

#### Translation strategy

- Every content row has zero or more translations in
  `cms_content_translations`. Same for terms in
  `cms_term_translations`.
- The current default locale is **`vi`**. All seed data, the Filament
  admin form, and the `findBySlug()` services default to this locale.
- The database, services, and API surface are **already multi-locale**.
  What is intentionally missing is a UI / language switcher: there is
  no admin page to manage locales yet.
- The future **Language plugin** (planned) will own:
  - available locales registry,
  - default-locale selection,
  - `hreflang` emission,
  - frontend language switcher,
  - translated admin UI.

Until that plugin lands, all writes use locale `vi`. Manual writes via
tinker / SQL can populate additional locales today — the schema and
services already accept them.

#### Slug strategy

`TheNguyen\CMS\Services\SlugManager` (singleton bound at `cms.slug`)
generates slugs with locale-aware rules:

| Script | Behavior |
| ------ | -------- |
| Vietnamese (`vi` or text containing `ăâêôơưđ`) | Vietnamese diacritics removed, `đ → d`, `Đ → D`, then `Str::slug`. `"Thiết kế website chuẩn SEO" → "thiet-ke-website-chuan-seo"`. |
| Latin (en, fr, es, etc.) | `Str::slug` defaults. `"Hello World" → "hello-world"`. |
| CJK / Arabic / Hebrew / Thai / Cyrillic / Greek / Devanagari (locale prefix OR script detection) | Characters preserved. Whitespace collapsed to `-`. Unsafe URL punctuation stripped. `"こんにちは 世界" → "こんにちは-世界"`. |

Uniqueness is per locale. `uniqueContentSlug` / `uniqueTermSlug`
append `-2`, `-3`, … on collision. `makeFullPath($slug, $prefix)`
prepends a route prefix:

- Pages → no prefix → `full_path = slug`
- Posts → prefix `blog` → `full_path = blog/{slug}`
- Categories → prefix `category` → `full_path = category/{slug}`
- Tags → prefix `tag` → `full_path = tag/{slug}`

These prefixes are stored verbatim in `cms_slugs` so the future
frontend router can resolve routes without rerunning slug rules.

Empty slug fallback: `content-{timestamp}` for contents, `term-{timestamp}` for terms.

#### Taxonomy strategy

`TheNguyen\CMS\Services\TaxonomyManager` (singleton at `cms.taxonomy`)
owns taxonomies and terms.

Core taxonomies seeded by `ensureCoreTaxonomies()`:

- `(content_type=post, slug=category, type=category, hierarchical=true, is_core=true)`
- `(content_type=post, slug=tag,      type=tag,      hierarchical=false, is_core=true)`

`is_core = true` rows must not be deleted via the admin
(`TaxonomyResource` disables the delete action for core rows). Custom
taxonomies are allowed (`type=custom`, `is_core=false`); the future
plugin/module system will add them at install time.

#### Content service

`TheNguyen\CMS\Services\ContentManager` (singleton at `cms.content`)
wraps creates/updates/deletes in a DB transaction and is the **only
write path** the Filament admin and seeders use.

```php
$content = app('cms.content')->create([
    'type' => 'post',
    'status' => 'published',
    'locale' => 'vi',
    'title' => 'Bài viết đầu tiên',
    'content' => 'Nội dung mẫu.',
    'term_ids' => [1, 2],
]);
```

On every write the service:

1. Creates or updates the `cms_contents` row.
2. Auto-generates the slug via `SlugManager` when empty.
3. Ensures slug uniqueness per locale.
4. Upserts the translation in `cms_content_translations`.
5. Syncs `term_ids` to `cms_content_terms` when provided.
6. Upserts the routing entry in `cms_slugs` with the right prefix.
7. Sets `published_at = now()` when status flips to `published` and
   no explicit date was supplied.

### Media Core (Phase 4A — current)

The Media Core is the minimal file subsystem added in **0.4.0**. It owns
two tables, one model, one service, a facade, and a small Filament
surface. It is deliberately limited to upload / browse / preview /
edit-metadata / copy-URL / delete.

**Tables**

| Table | Purpose |
| ----- | ------- |
| `cms_media` | One row per uploaded file. `disk`, `folder`, `filename`, `original_filename`, `extension`, `mime_type`, `size`, `width`, `height`, `path`, `url`, `alt`, `title`, `caption`, `description` (text, nullable — added in 0.9.3), `uploaded_by`. Soft deletes. |
| `cms_mediables` | **Structure only.** Polymorphic bridge (`media_id`, `mediable_type`, `mediable_id`, `collection`, `sort_order`) for a future attachment / Media-Picker phase. Not written to yet. |

**Storage layout**

Files are stored directly under `public/uploads/YYYY/MM` (e.g.
`public/uploads/2026/05`), consistent with `config('cms.paths.uploads')`
and the `public_root` deployment mode. Filenames are slugified from the
original name with a short random suffix to avoid collisions; the
original name is preserved in `original_filename`. Image dimensions are
read with PHP's native `getimagesize()` (SVG skipped). The `disk` column
records the logical label `public`; no storage symlink is required.

`public/uploads/.htaccess` (Apache 2.2 + 2.4) and `public/uploads/web.config`
(IIS) ship with the tree and disable script execution, directory listing, and
dot/sensitive-file access recursively — uploads are served as static data only
(see CMS_ARCHITECTURE.md → *Security architecture*).

**Service — `MediaManager` (`cms.media`)**

`upload(UploadedFile, array $meta = []): Media`, `delete(Media): bool`
(removes the physical file then soft deletes), `find(int): ?Media`,
`all(): Collection`. Exposed via the `Media` facade.

**Filament surface**

| Surface | Type | URL | Navigation |
| ------- | ---- | --- | ---------- |
| `MediaResource` | Resource | `/admin/media` | Group **Media** → **Library** |
| `MediaUpload`   | Page     | `/admin/media/upload` | Group **Media** → **Upload** |

The Library table shows Preview (image thumbnail or document icon),
Filename, Type, Size, Dimensions, and Uploaded, with View/Edit/Delete
row actions, bulk delete, and **Images**/**Documents** filters. Both
row and bulk delete remove the physical file through `MediaManager`.
The Upload page uses a multi-file `FileUpload` (max 20) wired to
`MediaManager::upload()` via `saveUploadedFileUsing()`. The Edit page
persists only the metadata fields (`alt`, `title`, `caption`,
`description` since 0.9.3) — the file cannot be replaced.

> **Metadata enrichment shipped in 0.9.3** — see the *Media Metadata
> Manager* phase note below for the `description` field, SEO helpers,
> upload alt defaulting, and the improved table/form.

> **Not in this phase:** Media Picker, editor integration, Theme
> Manager, Plugin Manager, S3/CDN, image crop/editor, WebP/AVIF, and
> galleries are all explicitly out of scope for 0.4.0.

### Media Picker (Phase 4B — current)

Added in **0.4.1**. The Media Picker is **app-level Filament UI
integration** only — it lives under `app/Filament/Admin/Components/` and
does **not** touch the Media Core in `packages/thenguyen/cms-core`. It
lets editors attach a featured image by selecting from existing media
rather than pasting a URL.

**Component — `App\Filament\Admin\Components\MediaPicker`**

`MediaPicker::make(string $field = 'featured_image', string $label = 'Featured image'): Group`
returns a Filament `Group`. As of **0.9.4** it is a WordPress-like **media
modal picker** (the searchable `Select` was replaced): a reactive preview
(empty "Add image" state, or the selected image + metadata with
**Replace**/**Remove**), an `Actions` row, and a `Hidden` field holding the
URL. **Add/Replace** opens a native Filament action modal with **Media
Library** (the `MediaLibrarySelect` thumbnail-grid field — search across
filename/alt/title/caption/description, details panel) and **Upload files**
(`FileUpload`, image-only, drag & drop → `MediaManager::upload()`) tabs. It is
reused by `PageResource` and `PostResource` and is suitable for future Theme
Options / Page Builder.

**Storage of the selected value**

`featured_image` currently stores a **URL string** (e.g.
`/uploads/2026/05/nguoi-dep.jpg`) in the existing
`cms_contents.featured_image` column (still true after the 0.9.4 modal
upgrade). No schema change, no migration, no relation is used yet. A cleared
selection is stored as an empty string (`''`) so it survives `ContentManager`'s
`$data['featured_image'] ?? $current` merge without modifying the core
service. A stored URL not found in `cms_media` still previews and is labelled
"External or missing media record".

> **Future option:** promote featured image to a `featured_image_media_id`
> foreign key, or use the reserved `cms_mediables` polymorphic relation,
> instead of a raw URL string. Deferred — the URL string is intentionally
> the simplest thing that works.

> **Still not in this phase (0.9.4):** multi-select/galleries, image
> crop/editor, folder manager, Theme Manager, Plugin Manager, and S3/CDN
> remain out of scope.

**Shared support — `App\Filament\Admin\Support\MediaItems` (0.9.5)**

The image list shown by the Rich Editor modal, the Featured Image
`MediaLibrarySelect` grid, and the `MediaPicker` preview all flow through this
one helper, so they stay byte-for-byte consistent: `imageQuery()` (base query,
newest first), `imageItems(int)` (normalised, max N), `normalize(Media): array`
(canonical shape incl. `seo_alt`/`seo_title`), `findByUrl(string): ?array`
(preview lookup), and `searchImages(string,int): array` (server-side LIKE over
filename/**url**/**path**/alt/title/caption/description, newest first). All
table/column-guarded.

**MediaPicker server-side search (1.0.0-beta.7.1.8)** — the
`MediaLibrarySelect` grid mounts the newest 50 but searches the whole table via
the authenticated `App\Http\Controllers\Admin\MediaSearchController`
(`__invoke`, limit capped at 100), registered as the
`filament.admin.cms-media-search` route on the admin panel's
`authenticatedRoutes`. The blade `x-data` debounces input and `fetch`es JSON
results; `getSelectedItem()`/`findByUrl()` resolve the current selection's
details even when it falls outside the snapshot. Degrades to client-side
filtering if the route can't be resolved.

**Media UX Polish (0.9.5)** adds table **bulk actions** — *Generate alt from
filename* (only where alt is empty) and *Clear metadata* — plus the same two as
**edit-page header actions** (with in-place form refresh), a Featured Image
**upload note** ("Uploaded image will be used as the featured image.") with a
pre-submit preview, and caption/description parity in the Rich Editor modal
search. No DB change. `/cms-health` reports `media_ux_ready`.

### Menu Manager (Phase 5 — current)

Added in **0.5.0**. Menus are **core CMS data** (not theme data) and live
entirely inside `packages/thenguyen/cms-core`. The admin UI is exposed
under a new **Appearance** navigation group.

**The Appearance group**

`Appearance` is the home for site-presentation tooling. It now contains
**Menus** and **Themes** (the Theme Manager joined this group in `0.6.0`).
The Theme Manager *declares* menu locations via `theme.json`; it does not
own the menu data.

> _Historical note:_ the rest of this section is the design as shipped in
> `0.5.0`, when the Theme Manager and frontend did not exist yet. Both now
> exist (`0.6.0` / `0.7.0`) — see those sections below.

**Menu locations**

A menu may be assigned a `location` string slot: currently `header`,
`footer`, or `sidebar` (see `MenuResource::locationOptions()`). As of
`0.7.0` the frontend renders these: `frontend_menu('header')` /
`frontend_menu('footer')` resolve the menu assigned to each slot and the
default theme's header/footer partials loop over the resulting tree.

**Tables**

| Table | Purpose |
| ----- | ------- |
| `cms_menus` | One row per menu. `slug` (unique), `location` (nullable), `status` (`active`/`inactive`), `is_system`, `sort_order`. Soft deletes. |
| `cms_menu_translations` | Translatable `name` + `description` per `[menu_id, locale]`. Default locale `vi`. |
| `cms_menu_items` | One row per item. `parent_id` (self-ref, nested), `type` (`custom`/`page`/`post`/`category`/`tag`), `reference_type` (`content`/`term`/null), `reference_id`, `url`, `target`, `css_class`, `icon`, `sort_order`, `is_active`. Soft deletes. |
| `cms_menu_item_translations` | Translatable `title` per `[menu_item_id, locale]`. |

**Multi-language posture**

Menu names and item titles are stored in translation tables keyed by
`locale`, exactly like Content and Term. The default locale is `vi`. Since
**0.9.2** both the menu name/description **and** the menu **item** titles are
edited per the selected Menu edit locale (`?locale=<code>`); item titles
default to empty when the selected translation is missing so it can be
created without overwriting another locale. Frontend rendering
(`frontend_menu()` → `MenuManager::tree()`) uses the current request locale.

**Service — `MenuManager` (`cms.menu`)**

`createMenu`, `updateMenu`, `deleteMenu`, `createItem`, `updateItem`,
`deleteItem`, `getMenuBySlug`, `getMenuByLocation`, `tree`,
`reorderItems`. Exposed via the `Menu` facade and the `menu()` helper
(`menu()` → manager; `menu('header')` → resolve by location then slug).
Item `reference_type` is derived from the chosen `type`. Page/post/term
items resolve their public URL from `cms_slugs.full_path` via
`MenuItem::resolvedUrl()`.

**Filament surface**

| Surface | Type | URL | Navigation |
| ------- | ---- | --- | ---------- |
| `MenuResource` | Resource | `/admin/menus` | Group **Appearance** → **Menus** |
| `MenuItemsRelationManager` | Relation manager | (on the menu edit page) | — |

Menu items are managed from the menu **edit** page through a relation
manager (no drag-and-drop tree, no separate cluttering resource). All
item create/update calls route through `MenuManager`.

> **Not in this phase:** Theme Manager, frontend menu rendering,
> drag-and-drop builder, Widgets, Customize page, and Plugin Manager are
> all explicitly out of scope for 0.5.0.

### Theme Manager (Phase 6 — current)

Added in **0.6.0**. The Theme Manager handles theme **discovery,
metadata, activation/deactivation, and asset publishing**. It does
**not** render any frontend — that is a later phase.

**No new table.** The active theme is stored in `cms_settings` under the
key `theme.active` (`is_public`, `autoload`).

> **Hardened in 0.9.7** (see [`CMS_ARCHITECTURE.md`](CMS_ARCHITECTURE.md) §10 and
> [`THEME_DEVELOPMENT.md`](THEME_DEVELOPMENT.md)): `active()` now returns an
> *effective* theme (stored → `default` → first valid → null); there is **no
> Deactivate action** — the admin only *switches* the active theme via a
> transactional `activate()` (validate manifest → verify required views resolve
> → publish assets → set `theme.active`; any failure leaves the previous theme
> active); theme manifests are validated (required `name`/`slug`/`version`/
> `author`; invalid ones are skipped and surfaced via `invalidThemes()`); and
> the frontend shows a 503 no-theme page when no valid theme exists.
> `canDeactivate()` returns `false`; `deactivate()` is programmatic-only and
> never sets `theme.active` null. The notes below describe the original 0.6.0
> shape.

**Theme directory layout** (`themes/{slug}/`):

```
themes/default/
├── theme.json          # metadata (name, slug, version, author, supports…)
├── screenshot.png      # admin preview (NOT web-served; shown as data URI)
├── functions.php       # config-returning; declares Theme Options schema (loaded safely, v0.9.9)
├── assets/{css,js,images}   # copied to public/themes/{slug} on activation
└── views/{layouts,pages,posts,partials}   # placeholder Blade (not wired)
```

**`theme.json`** declares `name`, `slug`, `version`, `author`,
`description`, `requires.cms`, and `supports` (`menus`, `theme_options`,
`widgets`). The `supports.menus` array is how a theme will *declare menu
locations* (e.g. `header`, `footer`) for the Menu Manager to fill.

**Support object — `TheNguyen\CMS\Support\Theme`**

A plain value object (not Eloquent, never persisted) built from
`theme.json`: `name`, `slug`, `version`, `author`, `description`, `path`,
`screenshot`, `supports`, `authorUri`, `supportEmail` (the last two added in
0.9.7), plus `toArray()`.

**Service — `ThemeManager` (`cms.theme`)**

`all()` (scan `themes/`, parse each `theme.json`), `find($slug)`,
`active()` (read `theme.active` setting), `activate($slug)` (validate →
store setting → publish assets), `deactivate()`, `themePath($slug)`,
`themeAssetsPath($slug)`, `publishAssets($slug)`. Asset publishing
**copies** `themes/{slug}/assets` → `public/themes/{slug}` (no symlinks,
shared-hosting friendly). Exposed via the `Theme` facade and the
`theme()` helper (`theme()` → manager; `theme('default')` → Theme;
`theme()->active()` → active Theme).

**Filament surface**

| Surface | Type | URL | Navigation |
| ------- | ---- | --- | ---------- |
| `ThemesPage` | Custom page (no Resource) | `/admin/themes` | Group **Appearance** → **Themes** |

The page shows a card grid (screenshot, name, version, author,
description) with an **Active** badge and **Activate**/**Deactivate**
actions. Screenshots are embedded as inline data URIs because the
`themes/` directory sits outside the web root.

> **Not in this phase:** frontend rendering, theme options editor,
> widgets, theme marketplace, ZIP installer, Plugin Manager, and Language
> Manager are all explicitly out of scope for 0.6.0.

### Frontend Rendering (Phase 7 — current)

Added in **0.7.0**. The public website is rendered with the active
theme. Default locale is `vi`.

**Active theme view namespace**

`ThemeManager::registerViews()` (called from `CmsServiceProvider::boot()`)
registers a `theme::` Blade namespace via `View::addNamespace('theme', …)`
with hint paths `[themes/{active}/views, themes/default/views]`. Laravel
resolves the first hint that contains a requested view, so a partially
overridden active theme inherits missing views from the default theme.
The call is wrapped in `try/catch` and never breaks boot. Theme views
reference siblings through the namespace
(`@extends('theme::layouts.master')`, `@include('theme::partials.header')`).

**Theme helper functions** (`cms-core/src/helpers.php`)

| Helper | Returns |
| ------ | ------- |
| `theme_asset('css/app.css')` | `/themes/{active}/css/app.css` |
| `theme_view('pages.page')` | `theme::pages.page` |
| `frontend_menu('header')` | menu tree array (or `[]`) |
| `content_url($content)` | `/{slug}` (page) or `/blog/{slug}` (post) |
| `term_url($term)` | `/category/{slug}` or `/tag/{slug}` |

**Rendering flow**

```
Request → frontend route → FrontendController
        → ContentManager / TaxonomyManager (published lookups, locale vi)
        → View::make('theme::…')  (active-then-default hint chain)
        → HTML (or graceful fallback if no theme view / 404 if not found)
```

- `home()` → published page `trang-chu` via `theme::pages.page`, else
  `theme::pages.home`, else a plain fallback.
- `page($slug)` / `post($slug)` → published page/post, else `404`.
- `category($slug)` / `tag($slug)` → term + its published posts via
  `theme::archives.index`, else `404`.

**Menu rendering flow**

`frontend_menu($location)` → `MenuManager::getMenuByLocation()` (then by
slug) → `MenuManager::tree()` → nested `['item','title','url','children']`
nodes the header/footer partials loop over.

**Route order (critical)**

Frontend routes load **after** `web.php` (cms-health), inside the `web`
middleware group, in this order: `/`, then the post/category/tag base routes
(`/{post_base}/{slug}`, … — registered **only when the base is set**), then the
**catch-all `/{slug}` last** (`@resolveSlug`, which dispatches via `cms_slugs`
to a page, base-less post, or base-less term archive). The catch-all has a
negative-lookahead `where` constraint excluding reserved single-segment
prefixes (`admin`, `cms-health`, `livewire`, `filament`, `storage`,
`uploads`, `themes`, `vendor`, `up`, `robots.txt`, `sitemap.xml`), so
admin/health/Livewire/Filament are never captured. The app's default welcome
`/` route was removed.

**Filament surface**

None — Phase 7 is public-facing only; no admin page/resource was added.

> **Not in this phase:** Rich Editor, Theme Options, Widgets, Customizer,
> Page Builder, Language Manager / multi-language URLs, advanced SEO, and
> Plugin Manager remain out of scope for 0.7.0.

### SEO Core (Phase 7.5 — current)

Added in **0.7.5**. A **lightweight** SEO foundation — no plugin, no
analyzer, no AI, no structured data. It resolves per-page meta from the
existing `meta_title` / `meta_description` / `meta_keywords` (content) and
term description fields, renders them through a theme partial, and serves
`robots.txt` + `sitemap.xml`.

**Service — `SeoManager` (`cms.seo`)**

Holds the SEO context for the current request. `FrontendController` calls
a context setter before rendering: `forHome()`, `forContent(Content,
locale)`, or `forArchive(Term, type, locale)`. Resolver methods —
`title()`, `description()`, `keywords()`, `canonical()`, `robots()`,
`ogTitle()`, `ogDescription()`, `ogType()`, `ogImage()`, `twitterCard()`,
`twitterTitle()`, `twitterDescription()`, `twitterImage()`, `current()` —
read by the theme SEO partial. Infra builders: `robotsTxt()`, `sitemap()`
(array), `sitemapXml()`. Exposed via the `Seo` facade and the `seo()`
helper.

**Resolution rules**

| Field | Order |
| ----- | ----- |
| Title (page/post) | `meta_title` → content title → site name |
| Title (home) | `general.site_name` → `TheNguyen CMS` |
| Title (archive) | `Category: {name}` / `Tag: {name}` |
| Description (page/post) | `meta_description` → `excerpt` → first 160 chars of content |
| Description (home) | `general.site_description` → `TheNguyen CMS website` |
| Description (archive) | term `description` → site description |
| Keywords | `meta_keywords` only |
| Robots | `settings('seo.robots')` → `index,follow` |

**Theme partial + layout**

`themes/default/views/partials/seo.blade.php` emits `<title>`, the
description/keywords/robots metas, `<link rel="canonical">`, Open Graph
and Twitter card tags from `seo()`. `layouts/master.blade.php` includes
it in `<head>` and no longer renders its own `<title>`.

**Infra routes**

`GET /robots.txt` (`cms.robots`, text/plain) and `GET /sitemap.xml`
(`cms.sitemap`, application/xml) → `SeoController` → `SeoManager`. Both
register in `routes/web.php` before the frontend catch-all so `/{slug}`
never captures them. The stock Laravel `public/robots.txt` was removed so
the dynamic route wins. `sitemap.xml` lists the homepage + published
pages/posts/categories/tags; only published content; no sitemap index.

**Health**

`/cms-health` now reports `seo_ready`, `sitemap_ready`, `robots_ready`.

> **Not in this phase:** advanced SEO plugin/analyzer, AI SEO, JSON-LD,
> sitemap index/pagination, per-record robots overrides, Rich Editor,
> Language Manager, Plugin Manager, Widgets, Theme Options, Page Builder,
> API Layer.

### Rich Editor + Media Insert (Phase 8 — current)

Added in **0.8.0**. The page/post **content body** is edited with
**TinyMCE** and stored as **sanitized HTML** (previously plain text).

**Field — `App\Filament\Admin\Components\RichEditor`**

A Filament `Field` (`RichEditor::make('content')`) backed by
`resources/views/filament/admin/components/rich-editor.blade.php`. TinyMCE
(v8, community/GPL) is **self-hosted** under `public/vendor/tinymce` and
loaded from `/vendor/tinymce/tinymce.min.js` — **no Tiny Cloud, no API
key**. Init uses `base_url: '/vendor/tinymce'`, `suffix: '.min'`,
`license_key: 'gpl'`. An Alpine component inside a `wire:ignore` wrapper
initialises it and syncs to Livewire with `$wire.set(statePath, html,
false)` (deferred), reading the initial value with `$wire.get`. Toolbar:
headings, bold/italic/underline/strike, link, lists, table, image (URL),
code view. Skin follows the admin light/dark class. Used by `PageResource`
and `PostResource` in place of the content `Textarea`. The `tinymce` npm
package is a dev dependency; its runtime assets are copied into
`public/vendor/tinymce`.

**Media insert** — three TinyMCE buttons: **Insert Media** (image media
modal, added in 0.8.1 — see below), **Insert media by URL** (prompt →
`<img src loading="lazy">`), and **Media** (opens `/admin/media` in a new
tab).

**Media Modal (0.8.1)** — an image-only picker inside `RichEditor` (no
new page/panel/table/route). `RichEditor::getMediaItems()` pulls up to 50
images from `cms_media` (newest first, table-guarded), embedded via
`@js(...)`; search is client-side. The **Insert Media** button opens an
Alpine modal (teleported to `<body>`) with a thumbnail grid + search;
selecting one inserts `<img src alt title width height loading>` into the
active editor and syncs Livewire. Modal state is per editor instance, so
multiple editors don't conflict. Inserted HTML still passes through
`HtmlSanitizer` on save. Empty state links to `/admin/media/upload`.

**Editor Polish (0.8.2)** — authoring-experience patch (no new
page/panel/table/route/migration). The Media Modal details panel gains
**Alt text** / **Title** / **Add caption** + **Caption** inputs;
unchecked inserts a plain `<img>`, checked inserts
`<figure class="cms-image"><img …><figcaption>…</figcaption></figure>`
(attributes + caption escaped). TinyMCE init adds paste cleanup
(`paste_data_images:false`, `paste_merge_formats:true`, `smart_paste`, a
`paste_postprocess` stripping inline `style`), link defaults
(`link_default_target`, `link_assume_external_targets`, `rel_list`), and a
skin-aware `content_style`. Default theme CSS gains `.cms-image` +
`.entry-content` editor-HTML styles (republished to
`public/themes/default`). `HtmlSanitizer` is **unchanged** — `figure`,
`figcaption`, and global `class` were already allow-listed.
`/cms-health` adds `editor_polish_ready`.

**Sanitizer — `HtmlSanitizer` (`cms.html`)**

`sanitize(?string): string`, DOMDocument-based, no new Composer package.
Allow-lists tags/attributes (see [`CMS_ARCHITECTURE.md`](CMS_ARCHITECTURE.md)
§11.6), drops `script`/`style`/`iframe` subtrees, unwraps unknown tags,
strips `on*`/`style`, blocks `javascript:`/`vbscript:`/non-image `data:`
URLs, and adds `rel="noopener noreferrer"` to external `_blank` links.
`ContentManager` sanitizes the body on **every write**.

**Frontend** — `theme::pages.page` / `theme::posts.post` render the body
with `{!! cms_html($body) !!}`. `cms_html()` sanitizes HTML; legacy
tag-less plain text is escaped + line-broken so old content still displays
without migration.

**Health** — `/cms-health` reports `rich_editor_ready`,
`html_sanitizer_ready`, and `media_modal_ready` (0.8.1).

> **Not in this phase:** media modal/grid picker, in-editor upload,
> multi-select, image crop/editor, S3/CDN, AI writer, plus all earlier
> deferrals (Language Manager, Plugin Manager, Widgets, Theme Options,
> Page Builder, API Layer).

## Public Runtime Structure

Everything browser-reachable lives in `public/`. The CMS introduces three
runtime-only subdirectories (none of them contain code; they only contain
assets that the CMS or its users place there):

```
public/
├── uploads/        User-uploaded media, organised as uploads/YYYY/MM/
├── themes/         Per-theme compiled / published assets
│   └── {slug}/
└── vendor/
    └── cms/        Assets shipped by the CMS itself
```

### Why assets belong in `public/`

- Webservers (Nginx, Apache, OpenLiteSpeed) only serve files that sit
  beneath the document root. Putting assets anywhere else either leaks
  source code or forces an extra proxy hop.
- Laravel's `public_path()` helper consistently resolves to `public/`,
  so URL generation and disk paths stay in sync.
- Shared-hosting deployments where the document root is the project root
  rely on the rewrite rules in `deployment/apache/` and
  `deployment/nginx/` to map `/foo.css` -> `public/foo.css`. Keeping all
  assets in `public/` is what makes that rewrite cheap and predictable.

### What does **not** belong in `public/`

- Source PHP for modules, themes, or the core (those live in `modules/`,
  `themes/`, `packages/`).
- Uncompiled source assets (those live in `resources/` or per-theme
  source folders).
- Anything writable that is not meant to be served (those live in
  `storage/`).

## Deployment Modes

The CMS supports four production layouts. The active mode is reflected
through the `CMS_DEPLOYMENT_MODE` environment variable so health checks
and dashboards can show it.

| Mode | Env value              | Webserver / host                                                |
| ---- | ---------------------- | --------------------------------------------------------------- |
| A    | `public_root`          | Shared hosting where `public_html` points at the `public` dir.  |
| B    | `public_html_rewrite`  | Shared hosting where the full project sits inside `public_html`.|
| C    | `public_root`          | VPS Nginx with `root /path/to/project/public`.                  |
| D    | `public_html_rewrite`  | VPS Nginx with `root /path/to/project` (rewrite to /public).    |

> Apache + OpenLiteSpeed map onto Modes B and D the same way: drop the
> Apache template in as `.htaccess`. OpenLiteSpeed respects `.htaccess`
> when "Allow override" is enabled.

### Shared Hosting Mode A — core outside `public_html`

```
/home/user/
├── laravel-cms/        (full project: app, bootstrap, vendor, etc.)
└── public_html/        (contents of laravel-cms/public)
```

- The `public_html/index.php` is edited so its `require` lines point at
  `/home/user/laravel-cms/...`.
- Apache uses the default `public/.htaccess` shipped by Laravel.
- **Pros:** most secure layout; only the contents of `public/` are web-
  reachable.
- **Cons:** requires the host to allow the document root to point at
  `public_html` (true for cPanel) and an `index.php` edit.

### Shared Hosting Mode B — full core inside `public_html`

```
/home/user/public_html/
├── app/
├── bootstrap/
├── vendor/
├── public/
├── ...
└── .htaccess           (from deployment/apache/root-public-html.htaccess)
```

- The `.htaccess` blocks sensitive files (`.env`, `artisan`,
  `composer.*`, `package*.json`, `phpunit.xml`) and framework
  directories (`app`, `bootstrap`, `config`, `database`, `modules`,
  `packages`, `themes`, `vendor`, `storage`, `tests`, `resources`,
  `routes`). All non-static traffic is rewritten into `/public/index.php`.
- **Pros:** zero-edit upload; works on every Apache-based shared host.
- **Cons:** the project root is the document root, so the security of
  the deployment depends on the rewrite rules being respected. Any
  webserver that disables `mod_rewrite` will leak source files.

### VPS Nginx Mode A — document root -> `/public`

- Use `deployment/nginx/public-root.conf`.
- `root /path/to/project/public;`
- **Pros:** standard, recommended Laravel layout. Fastest, simplest.
- **Cons:** requires full server access.

### VPS Nginx Mode B — document root -> project root

- Use `deployment/nginx/public-html-rewrite.conf`.
- `root /path/to/project;` with `try_files /public$uri ...`.
- **Pros:** mirrors the constrained shared-hosting layout while keeping
  Nginx's performance characteristics.
- **Cons:** more rules; PHP is scoped to `/public/.+\.php$` only.

### Phase 10.1 — Theme/Plugin ZIP Installer *(Done, 1.0.0-beta.2)*

Safe **local ZIP upload** install for themes and plugins. Core service
`ExtensionInstaller` (`cms.extension_installer`, facade `ExtensionInstaller`,

## Coding Standards

- **PSR-4 only.** No classmap autoloading. PSR-12 formatting.
- **`declare(strict_types=1);`** at the top of every new PHP file.
- **Service providers** are the only place that should touch
  `bootstrap/providers.php`. Modules should register their own service
  providers and let the module manager wire them up.
- **Config-driven**: features must read from `config('cms.*')`, not from
  hardcoded constants. Add new keys to
  `packages/thenguyen/cms-core/config/cms.php`.
- **Never hardcode paths.** Use the framework helpers
  `base_path()`, `public_path()`, `storage_path()`,
  `resource_path()`, `config_path()`, or the `CmsPath` accessors:

  ```php
  use TheNguyen\CMS\Support\CmsPath;

  $uploadsDir = CmsPath::uploads();
  $themesDir  = CmsPath::themes();
  ```

- **DTOs / value objects** for data crossing service boundaries
  (settings payloads, module manifests, theme manifests).
- **No raw SQL** in new code. Use Eloquent or the query builder.
- **All user input** must be validated at the framework boundary
  (FormRequest, Filament forms, or explicit DTO validation).
